# Authentication audit — 21 October 2026

## Baseline inspected before changes
No auth provider, auth backend, email/password, Google/Apple login, tokens, refresh, logout, account linking or account deletion exists. All use is local/guest; no Firebase project or OAuth configuration exists. RevenueCat is optional and uses an SDK-managed anonymous purchase identity after consent. Drift schema 2 has no user identity column: the library belongs to this installation, not an account. Signing in/out must never change or filter its rows, files or sync configuration. No source Git repository exists; source and original simulator data were backed up privately before this pass.

## Implementation decision
Add optional Firebase Authentication only (no Firestore, Storage, Analytics, Crashlytics or cloud screenshot sync), official Flutter Google Sign-In and native Apple authentication. Firebase supplies actual token verification, stable UID, refresh and account deletion without building an unverified local OAuth account system. Missing real dashboard configuration must leave guest use available and show unavailable sign-in controls. No Firebase anonymous account is needed for guest use. Firebase UID will be the sole authenticated RevenueCat app-user ID; never email/Apple relay address. Explicitly link another provider only after authenticating the current account, and never silently merge conflicting identities. Full results and external limitations follow after implementation.

## Implemented architecture and audit result

- Packages: `firebase_core 4.15.0`, `firebase_auth 6.7.0`, `google_sign_in 7.2.0` (Flutter-maintained official provider integration), `sign_in_with_apple 8.2.0` for native Apple authorization/button. Firebase iOS SDK resolves through SwiftPM; the final artifact must be checked for linked products, not merely every repository SwiftPM downloads. No email/password, phone/SMS, Firebase anonymous account, database, storage, app analytics or crash service was added.
- **Optional local guest first:** no account SDK initialization for a fresh guest. A preference stores only the user's decision to enable auth, not credentials/identity/Pro. With complete public configuration and prior auth use, Firebase restores its persisted session. Stale Keychain sessions on a fresh installation are signed out before an explicit new login can link anything. Missing configuration leaves guest features available and sign-in controls unavailable rather than simulating a successful login.
- **Google:** singleton SDK initialization is coalesced, uses the iOS/Web client IDs, requests only sign-in identity, exchanges its ID token through Firebase Auth, handles cancellation/provider/Firebase errors with localized messages. The iOS native callback scheme is generated from the public iOS client and verified against the actual built Info.plist before authenticating. No OAuth client secret is used by the app. Google native SDK handles callbacks; SceneDelegate remains FlutterSceneDelegate and plugins register with the existing implicit engine.
- **Apple:** native Apple sheet uses a fresh secure nonce and SHA-256 challenge; token and raw nonce are exchanged through Firebase Auth. Optional first name/email are accepted through Apple's credential; the UI falls back to account status when later grants omit them. Relay email is a normal provider address, never an identity key. On iOS foreground, Apple credential state and Firebase user/token validity are checked. Apple button is provided by the native-sign-in integration package, not an invented Apple logo.
- **Sessions and revocation:** Firebase owns refresh tokens/platform persistence (Keychain on iOS); app-owned preferences/Drift never store them. No independent encryption guarantee is made for Android SDK internals; Android backup is excluded and native validation remains pending. Foreground refresh reloads the Firebase user/forces token refresh and checks Apple credential state. Disabled/deleted/revoked/expired credentials return to guest and clear billing access; network failure retains the session/library for retry. No raw provider stack traces or tokens are presented/logged by application code.
- **Linking:** an already signed-in user reauthenticates their current provider before linking the new provider via Firebase linkWithCredential. Their UID stays unchanged. Account-already-in-use/duplicate-email cases show a conflict and never silently merge two UIDs or overwrite libraries. The user signs into the original identity before explicitly linking. A genuinely separate existing UID is not silently combined; support may be required to resolve existing provider conflicts.
- **RevenueCat:** after separate billing consent, Firebase UID is the only authenticated app-user ID, via SDK logIn; email/name are not subscriber attributes. SDK logOut is called only when it is currently identified, preventing a new anonymous ID every startup. Old-user entitlement is cleared immediately; identity mutations serialize with active store purchases and coalesce rapid changes. Only provider-verified active/unexpired pro grants the larger picker batch. Identity API failures block commerce while guest/local features continue; foreground refresh retries. RevenueCat aliases/transfer/restore behavior is server-configured and must be verified for both new and existing authenticated IDs; mocks do not prove cross-account subscription behavior.
- **Logout:** Firebase session and Google SDK session (initialized without an OAuth prompt when needed to clear a restored Google session) are signed out, auth auto-restore preference is disabled, RevenueCat transitions to anonymous, all local library/sync/language rows and image files remain untouched. Provider service cookies/Apple system account are outside the app; logout is not global provider-account deletion.
- **Delete Account:** explicit localized confirmation says local collections remain and subscriptions do not cancel. Fresh provider reauthentication precedes Firebase account deletion. For Apple, a fresh authorization code is revoked using Firebase's revocation API; failures are recoverable and do not report deletion as complete. Google disconnect is attempted after successful deletion. Firebase credentials clear and RevenueCat logs out, preserving financial/provider records according to the approved retention policy. No other account-owned server collections exist. RevenueCat erasure/support workflow and legally retained purchase records need owner policy approval; no secret management key is embedded to delete them.
- **Local data:** Drift remains schema 2, same database filename, IDs/media paths/preferences. No user_id column, ownership filter, sign-in migration that rewrites rows, account-created cloud copy, or delete-on-logout path exists. An account associates a subscription identity only. It is not a cloud backup or a privacy boundary between people sharing one unlocked device. The confirmation and Settings disclose that the installation's library is retained.

## Source data-flow verification

`Photos metadata/screenshot subtype or explicit PHPicker file → bounded private normalized image → Apple Vision → local rules → Drift/private image copy`. No image/OCR field is passed to Firebase, Google, Apple auth or RevenueCat. Auth flows carry provider credentials, UID and optional name/email to Firebase/provider; billing carries UID/purchase data after consent. Thus the UI's narrow **“Analiz cihazında yapılır”** is justified by source/data-flow review. This is not a packet-capture assertion that no network/OS/SDK metadata ever leaves the device.

## External limitations

No real Firebase/OAuth/Apple project values, provider authorization, token revocation, signed physical build, store identity alias/restore or account dashboard deletion was verified. Google and Apple code paths are implemented and mock-tested, but cannot be called production-complete until MANUAL_AUTH_AND_SERVICE_SETUP.md and physical acceptance checks are completed. The existing production release audit remains historical; PRODUCT_AUTH_VERIFICATION.md records this later pass.

Native dependency compatibility: Firebase Core 5/Auth 7 (iOS SDK 13) failed real SwiftPM resolution against Google Sign-In iOS 9 because their GTMSessionFetcher ranges do not overlap. Compatible published Core 4.15.0/Auth 6.7.0 (Firebase iOS 12.19.0) are selected instead; no SDK cache source or resolver constraints were patched. Preserve the lockfile and re-run native builds before upgrading this set.

Privacy limitation discovered in native SDK manifests: Firebase Auth declares operational diagnostic Analytics, and Google Sign-In declares linked service usage/device identifiers (plus broader identity/location categories). No supported blanket opt-out is asserted. Account/privacy UI and the current matrix disclose provider service metadata before optional sign-in. No separate app analytics SDK or screenshot payload is supplied. A request for social login necessarily adds off-device provider processing; the earlier no-cloud-OCR architecture remains unchanged.
